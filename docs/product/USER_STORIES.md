# Vibe Radar 首发用户故事

日期：2026-10-11（US-09 于 2026-10-13 随试玩运行时提案增补）。依据：[已采纳的 PRD v1.3](../../PRD.md)。首发 8 个故事已反哺 PRD 2.4 节、相关模块和附录 E26–33；US-09 为 Phase 2 场景，关联 PRD 3.2/4.5 与附录 E34–E38。以下人物与情境是设计示例，不代表已有访谈结论或真实用户数据。

首发要验证的行为是：读者找到值得看的产品，判断上手门槛，实际体验，回来反馈，并愿意再次使用。故事按这一过程排列；后台故事用于保障内容质量和持续服务。

## US-01 通勤时找到今天值得看的产品

**用户故事**：作为每天会刷 AI 工具的中文 builder，我希望在两分钟内看完今天的精选并选出一两个值得体验的产品，以减少在多个平台重复搜索的时间。

**具体情境**：小林09:00坐地铁时收到飞书卡片。距离到站还有两分钟，他打开日报，先看重点推荐，再决定点开哪个产品。两分钟是场景中的阅读预算，需要试读验证，不是已经达到的性能。

**主要流程**：飞书摘要 → 当日期号 → 扫描卖点、理由、门槛 → 查看项目。

**验收条件**：

- 日报有明确日期和精选总数，重点1–2条优先展示；每张卡能看到它是什么、为什么值得看及体验门槛。
- 同一产品在同一期只出现一次，多个来源可以共同列在该产品下。
- 360px宽手机上正文和操作可读，无横向滚动。
- 只有2条合格产品时显示2条短刊；0条时明确暂无推荐，不用旧产品冒充今日新品。
- 今日未发布时，首页显示最近一期的实际日期，不能把昨天内容标为今天。

**价值验证**：试读时观察读者能否在两分钟内选择条目，以及为什么点开或没有点开；用外链点击作为初步信号，不把点击直接认定为满意。

## US-02 用手机照着指南开始体验

**用户故事**：作为想看看新玩法、暂时没有电脑的读者，我希望照着几步指引就能看到产品的核心体验，以判断它是否值得之后深入研究。

**具体情境**：小周看到一个交互式创意作品，但不想先读长README。他选择标为“直接试玩”的条目，打开入口，照提示操作，观察指南指出的效果。

**主要流程**：查看体验方式 → 阅读最多4步指引 → 打开实际体验入口 → 完成第一步 → 观察核心效果。

**验收条件**：

- 指南明确“打开哪里、第一步、看什么、限制”，不使用只有宣传意义的“探索更多可能”等动作。
- “约30秒开始体验”只用于有实际验证记录的直接试玩条目；时间承诺不包含未说明的注册、安装和付款步骤。
- 产品需要登录时，在跳转前显示；目标平台不支持手机时明确标注，不引导读者以为可以手机直接体验。
- 需要安装或硬件的项目可以提供真实的公开演示，并显示“看演示”，不将演示写成已经动手试玩。
- 在材料中找不到的功能、按钮、测试输入或费用不能被补写为指南步骤。

**价值验证**：请未接触过产品的试读者照做，记录是否触达指南所说的效果、实际耗时和中断原因。

## US-03 决定一个工具值不值得安装

**用户故事**：作为想解决编码工作流问题的独立开发者，我希望在打开项目之前知道费用、系统要求和配置成本，以避免花时间安装后才发现无法使用。

**具体情境**：小陈用Windows，希望找一个能检查Agent是否弱化测试的工具。他看到推荐卡片，先确认是否支持Windows、是否需要API key，以及只能自托管还是有在线体验。

**主要流程**：查看适用场景 → 查看门槛 → 选择官网、仓库或演示 → 决定立即安装还是稍后处理。

**验收条件**：

- 费用、登录、API key、候补、自托管和平台分别表达，允许“收费且需要登录”同时存在。
- 费用或平台没有可靠依据时显示“未确认”，不能默认免费或跨平台。
- 需本地安装的卡片使用“安装体验”；准备时间没有验证时显示未知，不承诺30秒完成。
- 项目入口指向实际官网/仓库，来源与核查日期可见。
- MVP提供门槛信息即可满足故事，不因此新增高级筛选、自动安装或环境检测功能。

**价值验证**：询问试读者是否在跳转前做出了正确选择，统计“平台不兼容”“缺API key”“意外收费”等失败反馈。

## US-04 告诉主理人我的真实体验

**用户故事**：作为已经尝试过某个产品的读者，我希望无需注册就能表达“玩过了、觉得有趣、无聊或没玩起来”，以让后续精选和指南更符合实际体验。

**具体情境**：小林打开了一个工具，但步骤要求的入口不存在。他回到日报选择“没玩起来”。主理人修正指引后，他再次体验成功，能够修改之前的反馈。

**主要流程**：返回卡片/飞书反馈入口 → 提交试玩状态或评价 → 获得结果提示 → 需要时修改或撤回。

**验收条件**：

- 阅读和反馈不需要Vibe Radar账号；第三方产品自己的登录要求另行标注。
- “玩过了”与体验评价分开；评价“有趣/无聊/没玩起来”是当前单选态，允许修改和撤回。
- 重复点击不重复计数，网络失败有明确失败与重试提示。
- 正常匿名标识可用时，返回卡片或刷新能恢复当前反馈；“没玩起来”可选填原因，未填写保持未知。
- 飞书webhook链接打开反馈页，再由读者确认操作；链接预览机器人打开页面不能产生试玩或评价。
- v1反馈供主理人查看和调整规则，不因一两次反馈立即改变线上排序。

**价值验证**：关注自报试玩率、试玩后评价和失败原因；所有指标保留匿名身份与自报行为的局限。

## US-05 周末找回之前想玩的产品

**用户故事**：作为工作日没空安装工具的读者，我希望先收藏有兴趣的条目，周末在同一浏览器找回来，以便把发现转化为实际体验。

**具体情境**：小陈周三收藏了一个上下文工具，周六在同一台电脑打开收藏页，找到产品与当时的日报，再从仓库入口开始准备。

**主要流程**：卡片收藏 → 之后打开收藏页 → 查看产品及历史期号 → 开始体验或取消收藏。

**验收条件**：

- 无需登录即可收藏、取消和查看本浏览器收藏，刷新或关闭后重新打开仍保留。
- 收藏记录包含产品ID和来源期号，列表能回到收藏时的推荐内容。
- 清缓存或换设备不能同步，页面明确说明这一限制，不暗示云端收藏。
- 没有收藏时给出阅读入口；产品撤回时保留原因说明，不能继续显示正常体验承诺。
- 历史日报有永久链接和日期；产品当前简介变化不悄悄改写当时的卡片内容。
- MVP使用收藏页、日期页和产品历史即可，不因此新增全文搜索、账号或跨设备同步。

**价值验证**：记录收藏后是否回访、是否点击并自报试玩；不能把收藏数等同于实际体验数。

## US-06 核对信息并报告错误

**用户故事**：作为认真挑选工具的读者，我希望能查看推荐依据，并在链接、费用或步骤不正确时报告问题，以减少误导，也让后来的读者看到准确内容。

**具体情境**：小周发现卡片写“免费”，官网却要求付费。他打开来源确认后，提交“费用信息错误”，并附上一句说明。

**主要流程**：查看来源与核查时间 → 提交问题类型和短说明 → 主理人核查 → 查看公开更正。

**验收条件**：

- 每张公开卡片能查看原始来源和最近核查时间，普通读者不必理解内部证据ID。
- 支持报告入口失效、费用不符、平台不符和步骤错误，正常提交有结果提示。
- 内容问题当日进入复核；经核实的重要错误更正或撤下，显示原因与更正时间。
- 运营端报错状态与更正版本关联；不承诺向匿名读者私信通知。
- 历史原版本保留用于审计，读者默认看到更正版。
- 报错功能不顺带开放任意产品投稿，也不承诺即时处理所有报告。

**价值验证**：统计关键错误发生数、处理时间和更正后是否仍有人卡住；零报告不等于信息全正确。

## US-07 用十五分钟完成每日复核

**用户故事**：作为同时有其他工作的主理人，我希望在15分钟内完成关键内容复核，并保留已经编辑的结果，以持续运营而不必每天重新手工写日报。

**具体情境**：08:10候选已经生成，主理人删掉两个无法核验的条目、改掉一句夸张描述，把一个低热度创意项目排前。08:25离开，剩余候选按既有规则处理。

**主要流程**：查看最多60条候选 → 查来源与理由 → 通过/淘汰/改文案/调序 → 保存 → 确认定时发布或退出。

**验收条件**：

- 初版CLI即可完成操作；支持键盘选择、淘汰原因和撤销，代表候选20条的常规复核预算≤15分钟。
- 每次保存记录操作者、原因与版本；重启或退出不丢已经保存的内容。
- 08:35冻结时保留部分人工修改，未处理部分按自动规则完成。
- 无人复核时仍按质量门槛编制；不足就短刊，无合格推荐就空刊。
- 08:35前确认发布默认排队到09:00；发布后修改走更正版本，不覆盖历史记录。

**价值验证**：实际计时并记录额外查证耗时；主理人持续超过15分钟时，优先改候选质量和复核信息密度。

## US-08 处理部分发布失败而不打扰读者

**用户故事**：作为负责日更的运营者，我希望知道哪一步失败，并只恢复失败的部分，以保证读者能读到准确日报且不会收到重复通知。

**具体情境**：09:00网页公开成功，飞书发送失败。运营者查看发送账本，确认是请求被拒绝而非未知送达，恢复后只补飞书；网页和历史内容保持原样。

**主要流程**：接收需要处理的告警 → 查看阶段与渠道状态 → 核对送达 → 重放或补发明确失败的部分。

**验收条件**：

- 能区分源采集失败、生成失败、网页未公开和飞书发送失败，部分源失败不阻塞其他源的合格内容。
- 网页已成功时，补飞书不重建已公开快照，也不重复发送其他渠道。
- 发送超时且无法确认送达时标为unknown，不能盲目自动重发。
- 重放默认不对外发送；明确指定期号与失败渠道后才执行补发。
- 今日延迟时公开页面显示实际期号日期和状态，工程失败不伪装成内容正常的空刊。

**价值验证**：模拟一次网页成功/飞书失败与一次未知送达，检查恢复路径、告警是否可行动及重复通知数。

## US-09 一键试玩已核验的产品（Phase 2）

**用户故事**：作为已经选定值得体验产品的读者，我希望在日报里一键把产品装进本地工作区并打开终端式试玩，以把“从发现到体验”的步骤压缩到最少。

**具体情境**：小陈在卡片上看到某产品标注“一键启动（实测准备约 3 分钟）”，点击后进入 `/try/{slug}` 终端视图，观察安装日志；准备完成后按提示打开本地入口试玩，结束后由系统按 TTL 自动回收。

**主要流程**：查看 `try_tier` 与实测时间承诺 → 一键启动 → 观察准备日志（阶段与用时可见） → ready 后打开入口试玩 → 结束或等待自动清理。

**验收条件**：

- 一键入口只出现在已核验配方的条目上；tier 与时间承诺在启动前可见，无实测数据时显示“准备时间未验证”，不承诺一键。
- 沙箱只携带虚拟 key 与本地代理地址；真实 LLM key、宿主凭据与浏览器会话不进沙箱；会话预算超限即拒绝调用。
- 失败与超时明确显示阶段与可复制日志，不黑盒等待；连续失败的配方自动降级为 `guided` 并进入复核队列。
- 会话在独立根目录 `data/trials/<session_id>/` 运行，不写入仓库工作树；ready 后按 TTL（初值 2 小时）自动回收，`viberadar try clean` 可显式清理，会话目录不进备份。
- “玩过了”可附带会话证据（`trial_session_id`），自报与会话证据分开统计；启动成功不宣传为试玩完成。
- 本故事不改日报主流程、不加账号体系；`try_tier` 只展示、不默认加分。

**价值验证**：记录配方成功率、time-to-ready、失败阶段分布与试用会话数；先证明有人用，再讨论托管沙箱。

## 建议的开发顺序

先完成US-01、US-02、US-03，交付一份读者能理解、能选择、能触达入口的日报。接着完成US-04、US-06，建立体验反馈和纠错。US-07、US-08在正式试读前必须通过，US-05最晚在首发版本补齐。US-09 属 Phase 2，视试读与试玩运行时指标决定推进，不阻塞首发。

每阶段同时落实必要的来源、数据与质量检查，不能等所有页面完成后才验证采集和发布。故事顺序不改变PRD中的质量门槛与上线DoD。

## MVP 的用户价值验收

| 观察问题 | 对应故事 | 获取证据 |
|---|---|---|
| 读者能选出值得看的条目吗？ | US-01 | 限时试读、选择理由、点击 |
| 指南能帮助触达核心体验吗？ | US-02、03 | 照做观察、实际耗时、失败原因 |
| 体验结果是否能被准确表达？ | US-04、06 | 反馈/撤回演练、纠错处理 |
| 读者会回来继续体验吗？ | US-05 | 同浏览器回访、收藏后试玩 |
| 主理人能持续提供内容吗？ | US-07、08 | 复核计时、故障恢复与连续运行记录 |

本文件是开发与试读的故事基线，尚未代表这些场景已实现或验证通过。
