# Vibe Radar PRD 评审与补全建议

评审日期：2026-10-11。评审范围：原 `PRD.md`、`项目申报书.docx`、当前项目目录及关键平台官方文档。

**判断：产品定位值得保留，建议先证明读者愿意实际体验精选产品，再投入排序学习、个性化和更多分发渠道。** 当前最大缺口是可执行的产品规则与可复现证据。完整补全稿已更新到 [PRD.md](../../PRD.md)，原稿保存在 [原版 PRD](../archive/PRD-v1.0.md)。

## 1. 优先解决的问题

| 优先级 | 原稿问题 | 影响 | 补全稿处理 |
|---|---|---|---|
| P0 | 同时出现 08:00 管线完成、08:30 采集完成、08:13 发布和 09:00 推送 | 人工复核与数据截点无法同时满足 | 统一 07:30 数据截点、08:00 出候选、08:35 冻结、09:00 发布 |
| P0 | 自托管、API key、硬件项目也承诺 30 秒试玩 | 读者照做无法触达体验 | 区分直接试玩、观看演示、安装体验；30 秒承诺仅适用于已验证的直接试玩 |
| P0 | 同域名或同名即可合并；两个麦当劳 MCP 仓库被当作同一产品 | 错合并会污染产品档案和趋势 | 产品实体、发布事件、趋势主题分开；共享域名、同类工具不自动合并 |
| P0 | z-score、0–10 趣味分、新鲜度和规则分直接相加 | 配置权重不代表实际贡献 | 所有信号统一到 0–1；热度使用源内分位数；缺失速度有明确回退 |
| P0 | 默认自动发布，但失败、无好货、部分人工编辑没有统一规则 | 凑数、漏发、重复推送 | 发布状态机、质量门槛、短刊/空刊、截止时间、持久化发送账本 |
| P0 | 飞书机器人类型未区分，假定全部能直接回传按钮事件 | 首发交互可能无法落地 | MVP 用 webhook 推送并跳转网页反馈；原地回传需应用机器人集成验证 |
| P0 | 外链附加参数被当成点击追踪 | 服务端仍不知道谁点击；可能破坏签名 URL | 使用站内受控跳转 `/go/{link_id}`，只跳转已批准目标 |
| P0 | 只有精选日报文字，却承诺 136 条金样例召回验收 | 没有负例、遗漏列表和输入快照，无法计算召回 | 明确样例尚未成为机器可评测集，补原始输入、标签、实体关系和冻结切分 |
| P0 | PRD 成本上限 $2/天，申报书目标 $0.1/天 | 结题和工程预算不一致 | $0.1 定义为 LLM 优化目标，$0.5 告警、$2 硬上限；总运营成本单独算 |
| P0 | 原始 payload 存档与“不存全文”互相矛盾 | 数据保留范围不清楚 | 接入层字段白名单、证据摘录、短期抓取缓存、删除与备份周期 |
| P1 | 每期固定 8–15 条、全部源与完整后台都进入 MVP | 开发量和读者注意力失控 | 默认 6 条、常规 5–8 条；两源先跑通，PH 凭据可用后接入；后台先 CLI |
| P1 | 打开率、试玩率、周留存没有分母，飞书群阅读不可观测 | 指标看起来精确却不能核验 | 区分发送成功、网页打开、点击和自报试玩；飞书打开率记 N/A |
| P1 | “玩过了”自动改权重，低分和新账号容易被特殊对待 | 反馈偏差、恶意刷分、压制真正新产品 | v1 反馈先观测，调整需主理人确认；缺乏证据不判 spam |
| P1 | 阶段目标依赖搜索引擎收录、固定中文候选量和任意样本门槛 | 外部因素被当作交付能力 | 工程验收与运营效果分离；模型升级依据留出评测和真实反馈 |
| P1 | v1 匿名收藏没有说明存在哪里 | 用户误以为能跨设备同步 | 仅本浏览器 localStorage 收藏，明确限制，撤销反馈与清除入口齐备 |
| P1 | 发布内容随产品实体修改，历史一期会变 | 历史评测失真，无法审计更正 | 每期内容快照、版本号、更正记录，重放默认不对外发送 |
| P2 | 将两天观察写成市场空白、统计关系和成熟护城河 | 论证强度超出证据 | 保留为待验证假设，增加 2–4 周试读和用户访谈计划 |

## 2. 建议的首发产品

面向中文 AI builder，每天 09:00 提供一份短日报：优先展示今天最值得点开的 1–2 个产品，再给 4–6 个补充发现。每条明确“为什么值得看”“怎样触达核心体验”“是否要登录、付费、安装或提供 API key”。网页是完整阅读与反馈载体，飞书是分发入口。

首轮找 20–30 名目标读者试用两周；这个人数是招募目标，并非已存在的用户。先观察是否反复回来试玩、哪些指南让人卡住、主理人是否能在 15 分钟内完成复核。与读者平时单刷一个平台的方式做轻量对照，再判断多源策展是否值得持续运营。

第一阶段交付采集、去重、分类、证据型指南、确定性排序、CLI 复核、网页归档、飞书推送、基础反馈和失败恢复。RSS 可在复用同一刊物快照后加入。邮件、截图、中文社区桥接、完整后台、模型训练和个性化后置。

## 3. 外部依赖核查

- GitHub Search 单个查询最多返回 1,000 条；必须分页并记录 `incomplete_results`，不能称为全网全量采集。[GitHub 官方搜索文档](https://docs.github.com/en/rest/search/search)
- Product Hunt API 官方文档要求商业使用先联系平台；“公开 API”不能直接等同于商业使用已获许可。MVP 按研究/试读定位，商业化前核查授权。[Product Hunt 官方 API 文档](https://api.producthunt.com/v2/docs)
- PH GraphQL 配额按查询复杂度计算，并通过响应头返回剩余额度；不要与按请求次数计费的端点混用限额。[PH 官方限额文档](https://www.producthunt.com/v2/docs/rate_limits/headers)
- 飞书自定义 webhook 与应用机器人采用不同接入方式。补全稿先使用跳转网页反馈，卡片回传列为应用集成验证项。本次官方页面可访问，但正文未能通过文本检索读取；不得把完整回调能力写成已实测。[飞书自定义机器人指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[飞书卡片回调指南](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/handle-card-callbacks)
- DeepSeek 低价目标存在可行的理论依据，但要计算分层模型、缓存、失败重试和输出 token；供应商当前价格支持推算，不代表本项目已经达到预算。[DeepSeek 官方价格页](https://api-docs.deepseek.com/quick_start/pricing/)

## 4. 与申报书需要同步的表述

申报书保留原文件，本轮没有修改。建议后续同步：

1. 将“全网”“全量”“市场空白”“关键假设已被验证”改成有采样范围的初步观察。两天反例不能证明整体社区分数与趣味度不相关，也不能证明不存在竞争者。
2. 将已有工作拆成“项目方描述”与“可提交证明”。当前目录未发现管线代码、采集快照、试玩包、完整负例和运行日志；这些可能存在于其他位置，本次不能据此认定不存在。
3. 区分 LLM 单日优化目标、异常日硬上限、基础设施月费、人工时间和开发费用；按部署时价格及实际账单重算。
4. 将个性化策展和自动试玩包明确为后续研究方向。首发兑现公共精选与体验指引；任意第三方仓库自动安装执行需要单独的隔离与权限设计。
5. 日报打开率与订阅留存仅在具有相应可观测渠道和身份口径时考核；飞书群推送成功不等于用户阅读。
6. 90 天自动运营可以作为结题目标，工程上线先通过 7 天连续运行和 30 天稳定性观测；短刊/空刊与“有效产品日报”分开统计。

## 5. 完整稿的默认决策与待确认项

完整稿采用的建议默认值：中文、公开网页、飞书首发、匿名反馈、默认 6 条、质量不足短刊、复核可选、07:30 截点、09:00 发布。它们是本轮产品建议，尚未代表项目负责人已确认上线参数。

真正需要负责人决定的事项：首批读者获取方式、PH token/可用资格、部署预算、是否以商业产品运行、上线后的内容与运维负责人。其他常规工程选择可以按完整稿推进设计，避免因品牌名或二期账号方案阻塞 MVP。
